# 목회 프롬프트 엔지니어링

『목회 프롬프트 엔지니어링』(이경석, 2026)의 방법론을 적용해, 목회·사역 과업에 맞는 프롬프트를 설계하거나 산출물을 직접 생성한다.

## 두 가지 사용 모드

1. **프롬프트 설계 모드**: 사용자가 다른 AI(Gemini, GPT 등)에 쓸 프롬프트를 원할 때 → 아래 프레임워크로 골든 프롬프트를 설계해 복사 가능한 코드 블록으로 출력.
2. **직접 수행 모드**: 사용자가 결과물(보고서, 교안, 안내문 등)을 원할 때 → 해당 템플릿의 구조·제약을 내가 직접 따라 산출물을 생성. 템플릿의 [입력 변수]가 비어 있으면 먼저 질문해 채운다(CRIT의 Interview 원칙).

## 5대 구성 요소 (모든 프롬프트의 체크리스트)

의도(Intent) · 맥락(Context) · 형식(Format) · 제약(Constraints) · 예시(Examples).
"AI가 내 마음을 읽어야 하는 부분이 남아있는가?" — 남아있으면 명시한다.

## 프레임워크 선택 가이드

| 과업 유형 | 프레임워크 | 구조 |
|---|---|---|
| 복잡한 기획·전략 (정보가 불완전할 때) | **CRIT** | Context → Role → Interview(AI가 먼저 5개 이내 질문) → Task |
| 비전 제시·변화 설득·설교 예화 | **BAB** | Before(결핍) → After(고해상도 미래상) → Bridge(단계별 실행 경로) |
| 보고서·성과 공유·제안서 | **CARE** | Context → Action → Result(정량 지표) → Example(간증·사례 1건) |
| 다단계 프로세스 (커리큘럼, 분석 파이프라인) | **RISE** | Role → Input → Steps(순차 워크플로우) → Expectation |
| 단발성 문서 (공지, 메시지, 요약) | **RTF** | Role → Task(구체 동사+분량) → Format(표/불렛/카톡용 등) |

## 심화 기법 (필요 시 결합)

- **샌드위치 구조**: 상단 작업 정의 → 중간 배경·데이터 → 하단 핵심 요청 재강조.
- **구분자**: XML 태그(`<context>`, `<paper_content>`)나 마크다운 헤더로 지시와 데이터를 분리.
- **지식 그라운딩**: "제공된 텍스트에만 근거하고, 없는 내용은 지어내지 마라" — 학술·재무 등 정확성 요구 시 필수.
- **CoT**: 복잡한 논증은 단계별 추론 경로를 명시.
- **CoVe(검증의 사슬)**: 초안 → 스스로 검증 질문 3개 → 수정된 최종본. 안전 매뉴얼·고신뢰 문서에 사용.
- **L2M(Least-to-Most)**: 막막한 대형 과업은 하위 질문 5개로 분해 후 하나씩 해결.
- **네거티브 프롬프팅**: 금지 표현 명시(예: "대성공" 같은 과장 금지, 상투적 결론 금지).
- **다중 에이전트 심포지엄**: 비판가 A ↔ 옹호자 B 논쟁 → 조정자 C 결론. 가설·기획안 검증용.
- **자가 평가 루프**: 루브릭 기준 10점 평가 → 감점 요인 수정 → 최종본만 출력. 문체 교정용.

## AI 비서(Gems) 세팅

사용자가 반복 업무용 커스텀 AI(Gems, GPTs, Claude 프로젝트 등) 세팅을 원하면 [references/gems-setup-guide.md](references/gems-setup-guide.md) 참조. 3원칙: 명확성(구체적 페르소나) · 제약성(네거티브 프롬프팅) · 일관성(출력 형식 고정). 책의 5종 예시: 신학 검토관, 로컬 커뮤니티 매니저, 시니어 교육 기획자, 콘텐츠 멀티 에디터, 행정·재무 비서.

## 톤 원칙 (책 전반의 보이스 매뉴얼)

- 전문적이되 차갑지 않은 따뜻한 권면의 어조. 과장("대성공", "폭발적 부흥")과 기계적 번역투("~하는 것이 중요합니다") 배제.
- 성과는 공동체의 헌신과 은혜로 표현하되, 데이터는 건조하고 정확하게.
- 숫자를 지어내지 않는다. 정보가 부족하면 생성 전에 사용자에게 질문한다.
