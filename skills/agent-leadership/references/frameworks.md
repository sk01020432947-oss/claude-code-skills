# 프레임 원문 — 정의와 판정 기준

> 원본: 티타임즈TV, 강정구(라이너 AI전략 총괄) 인터뷰, 2026-08-12.
> 각 절의 **정의**는 원본 발언 기반, **판정 기준**은 실행 가능하게 붙인 보조 장치다.

---

## 1. 기업이 AX로 가는 4단계 여정

리더가 AI를 쓰기 시작하면 순서대로 이 벽을 만난다.

1. **체험** — 빠르게 발전하는 AI 서비스를 리더가 직접 써 본다.
2. **용어의 함정** — 에이전트·스킬·MCP·하네스·루프·그래프 엔지니어링이 쏟아진다. 우리 조직이 이미 쓰던 단어·체계와 어떻게 융합할지 정의해야 한다.
3. **시스템 연결** — 사내 기존 시스템과 붙여 에이전트가 실제로 일하게 만든다. **여기까지 간 회사가 아직 많지 않다.**
4. **AX(AI Transformation)** — 3단계가 되어야 비로소 도달한다.

> 판정: 3단계 이상 사례를 사내에서 3개 이상 댈 수 있는가? 없으면 조직은 1~2단계다.

## 2. AX 3축 지도

AX를 세 기둥으로 나눈다.

### 축 1 — 프런티어 모델 (기술 판단)
- 프런티어 모델을 어떻게 확보할 것인가. 못 쓴다면(보안·규제) 그 성능에 준하는 LLM을 내부에 어떻게 구축할 것인가.
- 성격: 기술 영역. 보안·비용·회사 맥락 적합성의 3중 최적화.
- **리더가 먼저 물어야 할 것**: 모델 선정보다 "이 모델로 내 업무에서 어디까지 끌어낼 수 있는가".

### 축 2 — 컴퍼니 브레인 (조직 지식)
실리콘밸리에서 유행하는 개념. 세 개의 하위 축으로 구성된다.

| 하위 축 | 내용 |
|---|---|
| 스킬 라이브러리 | 각자가 쓰는 스킬(≒에이전트)의 조합 라이브러리 |
| MCP 커넥션 리스트 | 사내 시스템과의 연결 목록 |
| 날리지 베이스 | 암묵지를 AI가 이해할 수 있는 형태로 표현해 둔 것 |

- 성격: 의사결정 영역. 방법론은 이미 상당히 정해져 있고, 컨설팅·사내 DX 전문가 자원도 많다. 관건은 "레거시 프로세스와 어떻게 융합할 것인가"라는 결정.
- **핵심 함정**: 한 번 만들고 끝나는 구축 프로젝트로 보면 실패한다. 누적·업데이트되려면 **소통·보고 체계 자체가 바뀌어야 한다.**
- 라이너 실제 사례: 1인 1에이전트가 슬랙에 상주 → 한 명이 에이전트로 지난 한 달 논의를 정리한 뉴스레터를 발행 → 그 뉴스레터가 곧 컴퍼니 브레인의 누적물. 보고서는 노션 한 줄 + 30분 퀵 캐치업 수준으로 축소. 대기업에서는 "파워포인트를 없애고 HTML 슬라이드로 보고한다"는 변화가 시작점으로 관측됨.

### 축 3 — 휴먼-에이전트 팀 (HAT, 別稱 "모자")
- 인간이 일하는 환경 = **휴먼 하네스**, AI가 도는 환경·가드레일 = **AI 하네스**. 둘이 만나면 **메타 하네스**가 되고 복잡도가 급증한다.
- 성격: **AI의 영역이 아니라 인사·조직·문화의 영역.** AX는 여기서 좌절하거나 병목이 생긴다.
- 1·2번은 WHAT에 가깝다(무엇을 할지 정하면 계획대로 간다). 3번은 WHY와 조직의 히스토리에 얽혀 있다.
- 엄밀히는 AX의 한 부품이지만, 과장해서 말하면 **AX의 전부**일 수 있다.

> **바이브 코딩 함정**: 고객사들은 대부분 "1번(어떤 모델)"과 "5번(이 업무를 AI로 전환)"만 묻는다. 그 상태를 흔히 바이브 코딩 레벨이라 부르는데, 바이브 코딩과 AX 사이에는 엄청난 간극이 있다. 1번의 **왼쪽(업무 구조 이해)**, **오른쪽(협업 구조 구축)**, **아래(가드레일·담당자 성장 경로)**가 실제로는 더 중요하다.

## 3. AI 활용 6레벨 (자율주행 L0~L5 차용)

"AI 잘 쓰세요?"라는 질문은 무의미하다 — 다들 챗GPT·제미나이·클로드를 쓰고 있으니 모두가 "잘 쓴다"고 답한다. 그래서 레벨을 나눈다.

| 레벨 | 상태 | 판정 신호 |
|---|---|---|
| L0 | 미사용 / 검색 대체 | 단발 질문, 결과 복붙 |
| L1 | 보조 사용 | 초안·요약·번역을 사람이 매번 지시 |
| L2 | 반복 프롬프트 자산화 | 자주 쓰는 프롬프트를 저장·재사용 |
| L3 | 조건부 자동화 | 바이브 코딩으로 워크플로를 자동화 |
| L4 | **하네스 엔지니어링** | 멀티모델·멀티에이전트 오케스트레이션 설계 |
| L5 | **루프 엔지니어링** | 시작·정지 조건을 설계해 자율 순환시킴 |

- 개발 영역에는 L5가 존재하지만, **비즈니스 리더 관점에서 L4~L5로 가는 것이 결정적**이다.
- 승급은 "도구를 더 많이 쓰는 것"이 아니라 **설계 대상이 바뀌는 것**이다: 답 → 프롬프트 → 워크플로 → 팀·가드레일 → 순환 조건.

### 하네스 엔지니어링의 6요소
롤에서 시작한다.

1. **롤(Role)** — 어떤 에이전트인가
2. **평가 기준** — 이 에이전트가 "일을 잘한다"의 정의
3. **컨텍스트** — 활동 배경 지식
4. **도구** — 무엇을 쓸 수 있나
5. **일하는 순서** — 워크플로
6. **가드레일** — 지켜야 할 선 ← **조직 관점에서 가장 중요**

> 어떤 LLM을 쓰느냐도 중요하지만, 조직에서는 가드레일이 정말 중요하다.

### 루프 엔지니어링
- 하네스를 한 바퀴 돌려서 **어떤 기준으로 시작하고 언제 멈출 것인가**를 설계.
- 필수 설계 항목: 트리거 조건 / 정지(스톱) 요건 / **인간이 어디서 개입할 것인가**(human-in-the-loop).

> 주의: 느슨한 하네스가 더 나을 때가 있다. 원본 발언 — Opus 5 등장 이후에는 하네스를 세게 주기보다 **느슨하게 주니 모델이 구조를 더 잘 짰다**. 하네스는 조이는 장치가 아니라 맞추는 장치다.

## 4. 80명 에이전트 7단계 파이프라인

작년엔 혼자 일했고, 지금은 **약 80명의 에이전트와 함께 일한다**. 80명을 관리하기는 쉽지 않으므로 7단계로 나눈다.

| 단계 | 이름 | 담당 | 비고 |
|---|---|---|---|
| 1 | **목표 설정** | **사람** | 절대 위임하지 않는 자리 |
| 2 | 형식·팀 구성 (캐스팅) | 오케스트레이터 AI | `캐스팅` 스킬 = 에이전트 팀 빌더. 50인 풀에서 선별 |
| 3 | 실행 | 선발된 에이전트들 | 자주 쓰는 업무 상황 약 35종을 미리 프롬프트 구조로 짜 둠 |
| 4 | 리뷰 | Five Colors 5인 | 아래 참조 |
| 5 | 윤문 | `토익 코리안`류 스킬 | AI스러운 문체 제거(휴머나이징) |
| 6 | 검증 | 팩트체크 에이전트 다수 | 토큰 여유가 있으면 "모든 출처를 다 레이어로 검증하라" |
| 7 | **판단** | **사람** + 어드바이저 25인 | 절대 위임하지 않는 자리 |

- 구성: **50(실무 팀원) + 5(리뷰어) + 25(어드바이저) = 80**
- 50인은 **비즈니스 리더가 일하는 순서대로** 편성됨: 전략기획실 → 마케팅 → 디자인 → 인사 → 재무 → 법무 등, **개발을 제외한** 비즈니스 직무 중심.
- 실행 방식: 상황별 프롬프트 구조를 미리 만들어 두고 **클로드/챗GPT의 프로젝트 기능에 붙이면 바로 돌아간다.**
- **1번과 7번이 있기에 내 자리는 사라지지 않는다**는 것이 발언자의 결론.

### Five Colors — 리뷰 5인 페르소나

| 색 | 역할 | 유래 |
|---|---|---|
| 블랙 | 집필자 | 펜의 색 |
| 레드 | 비판자 | 레드팀 |
| 블루 | 옹호자 | 블루팀 |
| 실버 | 전문가 | 중립·기술 판정 |
| 골드 | **돈 내는 사람** — 상사 또는 고객 | 금 = 돈 |

> 기억하기 쉬운 이름으로 페르소나를 짜는 것 자체가 설계의 일부다. 바로 떠올릴 수 없는 구조는 쓰이지 않는다.

### 어드바이저 25인 (판단 보조)
철학자 / 전략가 / 의사결정 / 기술 / 투자 관점으로 25인을 정의. **이순신 장군 포함.** 각자 시스템 프롬프트를 만들어, 어려운 주제에서 판단에 조언을 주는 그룹으로 운용한다. 의사결정 레벨에 있는 경영자들이 특히 좋아하는 장치.

> 영감 출처: 라이너 스칼라(논문 지원 프로덕트)의 멀티에이전트 구조 — 가설 수립 → 검증 → 연구 흐름 분석 → **5인 학자 피어 리뷰**(멀티 페르소나). 이 피어 리뷰 단계가 Five Colors·어드바이저 보드의 원형.

## 5. 피플 리더십 vs 에이전트 리더십

| | 피플 리더십 | 에이전트 리더십 |
|---|---|---|
| 핵심 질문 | **WHY** — 동기 부여 | **WHAT** — 목표와 태스크 설계 |
| 무게중심 | **평가** (채용 후 해지가 어려우니 교육·배치로 동기를 지킨다) | **채용** (안 돌아가면 지우고 새로 만든다) |
| 리더가 실제로 할 수 있는 것 | 인사 6단계 중 사실상 평가뿐 | 6단계 전부를 직접 설계 |

**인사 6단계 매핑**: 채용 · 교육 · 배치 · 평가 · 승진 · 보상

- **승진 = 이 에이전트에게 얼마나 많은 자율성을 줄 것인가.** 자율성을 주느냐, 어디까지 주느냐는 철저히 리더의 의사결정 영역이다.
- 그래서 **피플 리더십을 끝까지 해 본 리더가 AI를 잘 쓸 수 있다.** 에이전트를 쓴다는 것은 6단계를 똑같이 다 하는 일이기 때문.
- 실리콘밸리 개발자 영역에서 부각되기 시작했으나, 앞으로 비즈니스 리더에게 더 부각될 키워드. HAT(3축)를 푸는 핵심 열쇠.

## 6. 변화관리 — 저항감과 두려움

- AX를 한다고 하면 **일단 무조건 저항감부터 생긴다.** 그 정체는 대개 두려움.
- 그런데 **조직원은 두려움을 말하기 어렵다.** "해 봐라"에 "저는 두렵습니다"라고 답하는 순간 도태되는 느낌을 받기 때문. 많은 사람의 마음속에 있지만 표면에 안 나온다. 이걸 푸는 것이 리더의 가장 중요한 변화관리.
- 관측: **잘하는 사람일수록 두려움이 커진다** — 할 수 있는 게 더 많이 보이기 때문(진행자 이중학 교수).
- 처방의 방향: 효율화한 시간을 어디에 쓸지 **역할과 시간의 물꼬를 터 주는 것**. 정답은 조직 문화에 맞게 찾아가는 수밖에 없다.

### X톤 (Executive Hackathon)
- 해커톤을 하면 보통 막내를 시킨다 → 반대로 하자는 제안. **X톤 = eXecutive + hackathon**(발언자 조어).
- 설계: 특정 직급·연차로 묶어 해커톤 → 발표 → 후하게 포상 → **전사 라이브 생중계**.
- 근거: 리더들은 두려워한다. 그 리더가 **두려움 없이, 재미있게 쓰고, 성과를 만들어내는 걸 보여주면** 그만한 변화관리가 없다.
- 뒷받침: 마이크로소프트 Work Trend Index(2026)의 프론티어 펌 1번 특징 — **리더가 공개적으로 활용하고 공유하라.**
- 부작용도 인정: 스트레스, 정해진 시간에 만들어야 하는 답답함. AI 회사조차 전원이 잘 쓰는 것은 아니다.

## 7. 결론 — 개인의 증강에서 조직의 증폭으로

- **개인 관점**: AI는 도구를 넘어선 동반자·동료. "증강(augmentation)". 도구가 아니라 파트너로 볼 것 — 파트너라고 부르는 순간 의사결정자의 옆자리에서 돕는 역할이 된다.
- **조직 관점**: 개인이 AI를 잘 쓴다고 조직 AX가 성공하는 것은 아니다. 조직이 성공하려면 개개인의 노하우를 **증류(distill)**해 **암묵지를 자산화**해야 한다. 프로세스일 수도, 개인의 노하우일 수도 있으며 그 안에 저항감이 존재한다 → **조직 문화로 풀어내는 것이 관건.**
- **전제조건**: 조직이 증류를 잘하려면 **개인이 AI를 정말 잘 써야 한다.**
- **다음 지형**: 에이전트가 브랜드를 찾고 쇼핑하고 거래하는 **에이전트 이코노미**가 열린다 → "우리 브랜드가 AI 시대에 살아남고 있는가".
- **개인의 생존축**: 좋은 학교·좋은 회사·승진이라는 정해진 커리어 패스가 무너지는 중. AI 시대일수록 **차별적 내러티브** — 어떠한 의미로 살아낼 것인가 — 가 중요해진다.
