# LLM 판단 vs 코드 처리 구분

작업 흐름의 단계마다 처리 주체를 정한다. 나누지 않으면 Claude Code가 판단이 필요한 일(번역, 요약, 품질 평가)까지 스크립트로 처리해 품질이 떨어지거나, 반대로 결정론적인 일을 매번 LLM에 맡겨 결과가 흔들린다.

> 원칙: **재현성과 실패 복구가 중요하면 스크립트**, **판단이 필요하거나 패턴이 다양하면 에이전트(LLM)**.

## 기본 구분

| LLM이 직접 수행 | 스크립트로 처리 |
|---|---|
| 분류, 의사결정, 우선순위 판단 | 파일 입출력, 데이터 파싱 |
| 품질 평가, 정성 분석 | 외부 API 호출 |
| 맥락 기반 추론 | 반복, 집계 |
| 자연어 생성·요약·번역 | 정적 분석, 테스트 실행 |

## 경계 사례

| 작업 | 판단 | 이유 |
|---|---|---|
| 데이터 정제(규칙 기반 필터) | 스크립트 | 조건이 명확하면 재현성이 중요 |
| 데이터 정제(맥락 의존 판단) | 에이전트 | "이 데이터가 유효한가?"는 판단이 필요 |
| 에러 메시지 분류 | 에이전트 | 패턴이 다양하고 새 유형이 등장 |
| 포맷 변환 + 예외 처리 | 스크립트 + 에이전트 폴백 | 정상 케이스는 스크립트, 파싱 실패 시 에이전트가 판단 |

## 설계에 남기는 형식

1단계 분석 결과에 아래 표를 채우고, 단계마다 상세를 적는다. 이 표가 3단계(에이전트)와 4단계(스킬의 `scripts/`) 배치의 근거가 된다.

```markdown
### LLM 판단 vs 코드 처리 구분

| LLM이 직접 수행 | 스크립트로 처리 |
|---|---|
| [판단·추론 작업 목록] | [결정론적 작업 목록] |

#### Step N: [단계명]
- 처리 주체: 에이전트 / 스크립트 (`scripts/xxx.py`)
- 입력: [이전 단계 출력 또는 초기 입력]
- 처리 내용: [무엇을 하는가]
- 출력: [형식과 저장 위치]
- 성공 기준: [이 단계가 끝났다고 볼 조건]
- 검증 방법: 스키마 검증 / 규칙 기반 / LLM 자기 검증 / 사람 검토
- 실패 시 처리: 자동 재시도(최대 N회) / 사람에게 넘김 / 건너뛰고 기록
```

사람 검토(Human-in-the-loop)가 필요한 단계는 "검증 방법: 사람 검토"로 표시하고, 오케스트레이터에서 그 지점에 멈추도록 한다.
